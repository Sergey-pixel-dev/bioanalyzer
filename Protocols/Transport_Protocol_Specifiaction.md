

## Протокол SeregaProtocol (SerProt) поверх UART — спецификация v0.2

### Структура фрейма

```
0xAA | type | seq | len_L | len_H | payload | CRC16_L CRC16_H
```

| Поле | Размер | Описание |
|---|---|---|
| Start | 1 B | Маркер начала `0xAA` |
| Type | 1 B | Тип пакета |
| Seq | 1 B | Порядковый номер, 0x00–0xFF, wraparound |
| Length | 2 B | Little-endian. Размер поля `payload` в байтах (0–65535) |
| Payload | 0+ B | Данные команды / ответа / ошибки / стриминга |
| CRC-16 | 2 B | Little-endian, покрывает `[type][seq][len_L][len_H][payload]` |

Поле `type`, `seq`, `len_L`, `len_H` **не экранируются** — они всегда в фиксированных позициях после стартового маркера.

---

### Escape-кодирование

Применяется **только** к полям `payload` и `CRC-16`. Поля заголовка (`type`, `seq`, `len`) escape не подвергаются.

| Исходный байт | В потоке |
|---|---|
| `0xAA` | `0xBB 0xAA` |
| `0xBB` | `0xBB 0xBB` |

---

### CRC-16

Алгоритм: **CRC-16/Modbus** — полином `0x8005` (reflected `0xA001`), init `0xFFFF`, XOR out `0x0000`. 

Покрывает `[type][seq][len_L][len_H][payload]` в исходном (неэкранированном) виде, до escape-кодирования.

---

### Типы пакетов

| Байт | Тип | Направление | Описание |
|---|---|---|---|
| `0xCC` | Command | Master → Slave | Команда с параметрами |
| `0xDD` | Response | Slave → Master | Успешный ответ |
| `0xEE` | Error | Slave → Master | Ответ с ошибкой |
| `0xFF` | Push | Slave → Master | Стриминговые данные (без запроса) |

---

### Seq ID

Master увеличивает `seq` на 1 при каждом новом запросе (wraparound 0xFF → 0x00). Slave копирует `seq` из Command в ответный `Response` или `Error`. Push-пакеты имеют собственный независимый счётчик `seq` на стороне slave — master использует его для детектирования потерь.

---

### Стриминговый режим

Slave начинает отправку Push-пакетов (`0xFF`) после получения соответствующей команды, прекращает после команды остановки или по внутреннему условию. Master не опрашивает — данные идут самостоятельно. Push-пакет не требует ответа от master.

Push-пакеты имеют **фиксированный размер payload** на протяжении одной сессии стриминга. Допустимые размеры чистой нагрузки: **32, 64, 128 или 256 байт**. Размер выбирается при старте стриминга и указывается в поле `len`.

```
Запрос старта:  0xAA  0xCC  [seq]  [len=0x02 0x00]  [cmd_id]  [mode|size]  [CRC]  
Ответ OK:       0xAA  0xDD  [seq]  [len=0x00 0x00]  [CRC]
Push:           0xAA  0xFF  [seq]  [len=0x20/0x40/0x80/0x00]  [data...]  [CRC]   ← непрерывно
Стоп:           0xAA  0xCC  [seq]  [len=0x01 0x00]  [cmd_id]  [CRC]
Ответ OK:       0xAA  0xDD  [seq]  [len=0x00 0x00]  [CRC]
```

> Примечание: `len=0x00 0x00` означает payload длиной 0 байт. Для Push-пакетов `len` равно выбранному фиксированному размеру (например, `0x20 0x00` = 32).

---

### Структура Payload для Command

Первый байт payload — `cmd_id` (идентификатор команды). Остальные байты — параметры команды. В Response и Error payload определяется командой.

---

### Коды ошибок

Payload пакета `0xEE` — один байт кода ошибки.

| Код | Описание |
|---|---|
| `0x01` | Неизвестная команда |
| `0x02` | Неверные параметры |
| `0x03` | Устройство не готово |
| `0x04` | Ошибка аппаратуры |
| `0x05` | CRC не совпал |
| `0x06` | Неверный размер payload |

---

### Таймаут и повтор

Master ждёт Response не более **T_timeout** (рекомендуется 100 мс для обычных команд). При отсутствии ответа повторяет запрос с тем же `seq`. Slave, получив Command с `seq`, совпадающим с предыдущим, может отправить кэшированный ответ — опционально для простых реализаций.

---

### Восстановление после сбоя

Приёмник, обнаруживший ошибку (неверный escape, CRC mismatch, или любое нарушение структуры), сбрасывает парсер в состояние ожидания стартового маркера `0xAA`. Байты до следующего `0xAA` игнорируются. Это обеспечивает быструю ресинхронизацию на границе пакетов.
